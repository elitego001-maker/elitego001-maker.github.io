HoundMasker — Privacy-Preserving Attack Path Analysis for BloodHound

A breakdown of how HoundMasker strips sensitive node data from BloodHound exports while keeping attack path graphs intact.

BloodHound is one of the most useful tools in an internal penetration test or red team engagement, but its output is a liability the moment it leaves a client's network. Usernames, group names, computer hostnames, and full attack paths sit in plaintext JSON — exactly the kind of data you don't want floating around in a report attachment, a shared drive, or a GitHub gist someone forgot to delete. HoundMasker exists to solve one narrow problem: how do you talk about an attack path without exposing who or what is actually in it?

Chapter 1 — What Is HoundMasker?

HoundMasker is a preprocessing layer that sits between a raw BloodHound export and anything downstream — a report, a screenshot, a shared Neo4j instance. It walks the JSON, replaces every identifiable node property with a deterministic pseudonym, and leaves the graph topology untouched. The result is a dataset you can share, archive, or hand to a third party without leaking a single real identity, while every relationship an attacker could exploit is still fully visible.

The goal isn't to anonymize the technique. It's to anonymize the people and machines the technique was demonstrated on.

Why This Matters

Most teams solve this problem by redacting screenshots after the fact, which is slow, error-prone, and falls apart the moment someone needs the underlying data for a re-test or a retrospective. Masking at the data layer means every downstream artifact — reports, dashboards, training material — inherits the protection automatically.

Chapter 2 — How the Masking Works

HoundMasker builds a deterministic mapping table keyed off each node's object ID, so the same principal always resolves to the same pseudonym across an entire dataset — DC01.CORP.LOCAL becomes something like HOST-7F3A.MASKED every time it appears, whether that's in a node property or an edge reference.

python 
def mask_identity(object_id: str, kind: str, salt: bytes) -> str:
    digest = hashlib.sha256(salt + object_id.encode()).hexdigest()[:8]
    prefix = {"User": "USR", "Computer": "HOST", "Group": "GRP"}[kind]
    return f"{prefix}-{digest.upper()}.MASKED"

Everything else — session data, ACL edges, group membership, delegation rights — is left exactly as BloodHound reported it. An analyst reviewing the masked graph can still trace a full path from an initial foothold to Domain Admin; they just can't tell you which real user or machine sits at each hop.

Running It

The CLI takes a raw export directory and a salt, and writes a masked copy alongside it:

bash 
houndmasker --input ./bloodhound_export --salt "$(openssl rand -hex 16)" --output ./masked_export

The salt is generated per engagement and never written to disk alongside the masked data, which means the mapping can't be reversed without it — even by someone who gets full access to the masked export.

  • Deterministic per engagement, not globally — the same host masks differently across two separate assessments
  • Topology-preserving — every edge, path, and privilege relationship survives untouched
  • Zero external dependencies beyond the Python standard library
Chapter 3 — Where It Falls Short

HoundMasker doesn't protect against re-identification from context. A masked graph with exactly one Domain Admin, one file server, and a distinctive OU structure can still be fingerprinted by someone who knows the environment. It also doesn't mask free-text fields like descriptions or SPNs that sometimes leak identity — those need to be scrubbed separately before an export is considered safe to share.

The full source, along with the mapping-table format and a test suite built against sample BloodHound exports, is available on GitHub. If you're regularly handing off attack path data to clients or teammates outside the assessment, it's a small tool that removes a recurring risk.
